공개 사이트를 보면 현재 WONT Travel Club은 이미 한달살기 맞교환 여행,
전세기 공유 플랫폼, 투어·티켓, 젯풀호스트 프랜차이즈, 여행 콘텐츠와
멤버십을 하나의 브랜드 아래 제시하고 있다. 특히 Local Life 페이지는
한국인과 외국인의 집 맞교환 및 현지 생활 경험을 사업 콘셉트로 명시하고
있으며, JETPOOL 페이지는 전세기를 공유하는 모델을 설명한다. 따라서 이번
사업은 완전히 새로운 브랜드를 만드는 것보다, 기존에 존재하던
‘교환·공유·여행’ 콘셉트를 실제 거래 가능한 양면시장 플랫폼으로
제품화하는 작업으로 보는 것이 맞다. [1]

현재 투어·티켓 공개 페이지는 일부 상품영역이 제목·가격 등의 템플릿
형태로 노출되어 있고, 회원가입 화면에서는
이메일·이름·비밀번호·전화번호와 약관 동의를 받는 전통적인 가입 흐름이
확인된다. 공개 화면 기준 Google/Kakao/Naver OAuth, 숙소 공급자용 PMS,
실시간 재고 잠금, 거래별 결제 상태머신, 교환계약, 가이드 매칭 등 본
백서가 요구하는 트랜잭션 플랫폼 기능은 확인되지 않았다. 이는 “없다”는
단정이 아니라 공개 프런트엔드에서 확인되지 않았다는 의미다. [2]

사이트 하단에는 호스팅 제공자로 Sixshop이 표시되어 있다. 따라서 소스코드
자체를 그대로 옮기는 “코드 마이그레이션”보다, 기존
콘텐츠·회원·미디어·SEO URL·운영 데이터를 추출한 뒤 새로운 애플리케이션과
데이터 모델에 적재하는 리플랫폼(re-platforming) 접근이 적절하다. [3]

핵심 결론

JETPOOL은 Airbnb Clone 하나를 포크해 확장해서는 안 된다. 숙박 예약과
Home Exchange, 유료/무료 가이드, 여행상품, 정산은 각각 다른 상태와 법적
책임을 갖기 때문이다. 공개 오픈소스는 기능별로 선별해 참조·통합하고,
사업의 핵심 IP인 Exchange Engine, Guide Matching, Compliance Gate,
Settlement Ledger는 자체 도메인으로 구축해야 한다.

채팅·온라인 상태·실시간 예약 알림에 사용할 수 있다. [4]

목표 기능과 플랫폼 아키텍처

누락 없는 기능 범위

JETPOOL은 단순 숙박 플랫폼이 아니라 서로 다른 네 가지 Marketplace를 한
계정·한 결제·한 신뢰체계로 통합하는 플랫폼이다.

Stay Marketplace는 숙소 등록, Host/Guest, 위치·가격·시설·인원·날짜 필터,
Map Search, 사진·동영상, 가용성 캘린더, 요금, 최소숙박일, Hold, 예약,
취소, 환불, 체크인, 리뷰를 담당한다.

Home Exchange는 사용자가 자신의 집을 exchange_enabled로 등록하고, 상대방
숙소와 날짜를 제안하며, 반대제안·상호수락·신원 및 숙소 검증·교환
약정·일정 블록·완료·상호 리뷰를 수행한다. 일반 숙박 Reservation에 이
과정을 억지로 포함시키지 않고 별도의 ExchangeRequest 및
ExchangeAgreement aggregate로 관리한다.

Guide Friend는 다음 네 유형을 분명하게 구분한다.

  ---------------------------------------------------------------------------
  유형              정의                결제              필수 검증
  ----------------- ------------------- ----------------- -------------------
  FRIEND            현지 친구·문화교류  원칙적 무료       본인확인·안전정책

  VOLUNTEER         자원 안내·교류      무료              본인확인·활동범위

  PAID              유료 현지 안내      유료              사업·자격·규제 검토
                                                          Gate

  PROFESSIONAL      전문                유료              사업자·관련
                    가이드/여행사업자                     자격·보험 등 검증
                                                          필드
  ---------------------------------------------------------------------------

Travel Commerce는 투어, 티켓, 액티비티, 패키지, 일정표, 옵션, 출발일,
재고, 최소 출발 인원, 공급자, 주문, 취소정책 등을 담당한다. 여행업을
실제 영위할 경우 관광진흥법상 등록 및 보증 관련 의무를 사업모델에
반영해야 한다. 관광진흥법 제4조는 여행업 등 해당 관광사업의 등록을
규정하고 있고, 시행규칙 제18조는 여행업자가 사업 전 보증보험·공제 또는
영업보증금 제도를 유지하도록 규정한다. [5]

Payment & Settlement는 PG 결제와 공급자 정산을 분리한다. TossPayments의
Payment 객체에서 paymentKey, orderId, 금액 및 결제상태를 거래 데이터와
함께 보관하고, 결제 승인·취소·Webhook은 서버측 어댑터가 수행한다. Toss
공식 API 문서는 paymentKey를 결제 조회·승인·취소에 사용하는 고유키로
정의하고 결제상태 및 webhook 검증 데이터를 제공한다. [6]

Trust & Operations에는 이메일·SMS·Push·In-app notification, P2P 채팅,
고객센터, 신고·분쟁, 리뷰·평점, Host/Guide 제재, 관리자 CMS, 통계,
공급자 정산, 세무자료, 감사로그가 포함된다.

Platform Engineering에는 Google/Kakao/Naver OAuth, 관리자·회계 계정 2FA,
이미지/미디어 Storage, Meilisearch, MapLibre, Realtime, CDN/WAF,
모니터링, CI/CD, 백업 및 재해복구가 포함된다.

핵심 설계 원칙은 PostgreSQL을 거래 사실의 Source of Truth로 유지하는
것이다. Meilisearch는 검색용 projection, Redis는 캐시와 rate-limit,
Realtime은 전달 채널이지 예약의 최종 진실이어서는 안 된다. Supabase
Realtime은 Broadcast/Presence/Postgres Changes를 지원하며, Realtime
Authorization은 RLS 정책을 이용해 메시지 접근을 제한할 수 있다. [7]

검색도 동일하다. Meilisearch는 full-text, faceting, fuzzy/geosearch 등
검색 기능을 제공하므로 properties, guides, travel_products의 후보 검색에
적합하지만, “특정 날짜에 정말 예약 가능한가”는 검색 인덱스가 아닌
Booking DB에 최종 확인해야 한다. Meilisearch 프로젝트 자체도 faceting,
typo tolerance, geosearch 등을 주요 기능으로 명시한다. [8]

공개 사이트가 Sixshop 호스팅을 이용한다는 것만 확인될 뿐 실제 Export
범위는 알 수 없으므로, 회원 비밀번호·결제정보를 스크래핑하는 방식은
사용해서는 안 되며 공식 Export와 사업자 권한 하의 데이터 제공 경로가
우선이다. [3]

예약 경쟁상태를 막기 위해서는 단순히 “조회 시 빈 방이었다”는 결과로
예약을 확정하지 않는다. write 시점에 availability를 다시 확인하고,
Hold를 DB transaction 안에서 취득한 뒤 결제를 진행해야 한다. Smoobu
Booking Engine의 구현 가이드 역시 브라우저의 가용성 상태를 신뢰하지 않고
서버가 live availability를 재검증하며 durable state machine과 webhook
reconciliation을 사용하도록 설계되어 있다. [10]

주요 이벤트는 property.published, availability.changed,
reservation.held, reservation.confirmed, reservation.cancelled,

모든 외부 webhook에는 provider event ID 또는 payload hash 기반
idempotency가 필요하다. Smoobu 공개 엔진도 webhook_events 및
idempotency_keys를 별도로 두고 webhook 중복처리 방지를 설계한다. [10]

초기 비동기 큐는 Postgres Outbox + Supabase Queues로도 충분하다.
Supabase Queues는 PostgreSQL 기반 durable queue로 제공되므로 초기
시스템에서 별도 Kafka cluster를 운영하지 않고도 비동기 작업을 시작할 수
있다. [12]

wrujel 프로젝트는 Next.js 13, TypeScript, Prisma, MongoDB, NextAuth
기반이며 Google/GitHub OAuth, 숙소 생성, 이미지 업로드, 날짜·인원 필터,
지도, 날짜 범위 예약, 즐겨찾기 등을 구현한다. schema.prisma에는 User,
Listing, Reservation 간의 기본 관계도 확인된다. 이는 JETPOOL
프런트엔드의 훌륭한 참고자료지만, 단순
Reservation(startDate,endDate,totalPrice) 모델은 JETPOOL의
Hold·결제·환불·교환 요구를 수용하기에는 부족하므로 그대로 사용하면 안
된다. [14]

Smoobu 엔진은 가장 중요한 참고 코드다. 공개 AGENTS.md가 AI 코딩
에이전트를 위한 통합 가이드로 작성되어 있고, api/, React widget,
Terraform infra/와 함께 booking state machine, DB 테이블, idempotency,
webhook 처리를 상세히 설명한다. 특히 booking_sessions, holds, payments,
webhook_events, idempotency_keys, audit_log 구조와 서버측 payment
confirmation 패턴을 JETPOOL Booking Service에 적극 반영할 가치가 있다.
다만 조사 시점 저장소 자체는 커밋 수가 적고 규모가 작은 프로젝트이므로
“production-grade”라는 작성자의 설명과 별개로 JETPOOL 배포 전 독립적인
코드·보안 audit가 필요하다. [15]

Medusa는 commerce building blocks를 제공하며 공식 저장소에는 packages/,
integration-tests/ 등이 존재한다. Medusa Core는 주문·프로모션·Commerce
workflow를 활용하는 데 적합하지만 Home Exchange 및 숙박 Hold를 Medusa
Order 상태에 종속시키지 않는 것이 중요하다. Medusa는 Core와 별도 상용
기능의 라이선스 경계를 두고 있으므로 Enterprise 기능을 채택할 경우 별도
계약을 확인해야 한다. [16]

QloApps는 PMS, Booking Engine, 호텔 웹사이트를 제공하는 호텔관리
시스템이며 현재 공개 저장소는 OSL-3.0으로 표시되어 있다. classes,
controllers, modules, admin-dev, themes, webservice 같은 구조를 분석해
객실·요금·PMS 관리자 업무 흐름을 추출하되, Jetpool Core에 그대로
복사하기 전 OSL 의무를 별도 검토해야 한다. [17]

Payload는 TypeScript/Next.js 기반의 오픈소스 CMS/관리자 프레임워크로 MIT
라이선스를 사용한다. JETPOOL에서는 여행지·스토리·FAQ·프로모션·패키지
소개 같은 콘텐츠에 사용하고, 예약·결제·정산의 Source of Truth는
PostgreSQL 거래 서비스에 남겨야 한다. [18]

MapLibre GL JS는 브라우저에서 interactive vector map을 구현하는
프로젝트이고 src, docs, ARCHITECTURE.md를 제공한다. 실제 운영 시 지도
렌더러와 별도로 tile/geocoding 공급자의 사용조건·비용을 산정해야 한다.
[19]

Novu는 Inbox, Email, SMS, Push, Chat 등 복수 채널을 하나의 workflow
모델로 다루는 오픈소스 커뮤니케이션 플랫폼이며, 저장소에는 MIT 코드와
enterprise license 파일이 함께 있다. JETPOOL에서는 직접 거래 메시지
저장소가 아니라 notification orchestration으로 사용하는 것이 적합하다.
[20]

Chatwoot은 오픈소스 live-chat/email/omnichannel support desk이며
Rails/Vue 코드와 app, db, deployment, docker 등을 제공한다. 이는
여행자↔호스트 P2P 대화 자체보다 고객센터, 분쟁, 운영상담에 배치하는 것이
구조적으로 깔끔하다. [21]

TossPayments 공식 샘플 저장소에는 Express+React, Express+Vue, Django,
Go, JSP, PHP, Spring 등의 연동 샘플이 있고 MIT 라이선스가 명시되어
있으며 공식 개발문서로 연결된다. [22]

인증·보안 모델

Supabase 공식 문서는 Kakao 로그인을 별도로 설명하고 MFA에서 TOTP 또는

이번 공식 문서 조사에서는 Supabase의 Kakao 문서는 확인했지만 Naver에

“Supabase가 기본 지원한다”고 전제하지 않고 custom OAuth adapter/Auth
broker로 설계해야 한다. Auth.js는 built-in 또는 custom OAuth provider
패턴을 제공하므로 대안이 될 수 있다. [24]

한국 숙박·여행업 Compliance Gate

가장 중요한 사업 리스크는 “누구나 집을 올릴 수 있다”는 제품 콘셉트와
“누구나 유료 숙박 영업을 할 수 있다”는 법적 자격을 혼동하는 것이다.

한국관광공사 Safe Stay의 현재 안내는 관광진흥법상 외국인관광
도시민박업이 도시지역 주택에서 외국인 대상으로 운영되며 원칙적으로
내국인 영업은 허용되지 않는다고 설명하고, 특정 예외를 별도로 제시한다.
또한 외국인관광도시민박업·한옥체험업·관광펜션업·호스텔업·농어촌민박업
등의 인허가 정보를 조회할 수 있다. [26]

따라서 JETPOOL은 다음 식의 rule engine을 가져야 한다.

    Listing Publish
         │
         ▼
    Property Type?
         │
         ├── Hotel / Hostel → 해당 등록정보 검증
         ├── Rural Minbak   → 농어촌민박 인허가 검증
         ├── Hanok          → 해당 인허가 검증
         └── Urban Home
                │
                ▼
          Permit Type / Guest Eligibility
                │
           ┌────┴─────────┐
           │              │
       legally allowed   not verified
           │              │
           ▼              ▼
       PUBLISH         BLOCK PAID BOOKING

Safe Stay는 인허가 데이터가 지방행정 인허가 데이터를 기준으로 제공되며
공공데이터포털에서 다운로드할 수 있다고 안내한다. 따라서
property_permits의 자동 검증 adapter를 만들 수 있다. [26]

Home Exchange도 금전이 없다는 이유만으로 모든 숙박 규제에서 자동
면제된다고 코드에 가정해서는 안 된다. 실제 제공 형태, 반복성, 대가성,
해외·국내 사용자, 주택 유형 등 법률적 사실관계에 따라 판단될 수 있으므로
exchange_legal_classification을 운영정책으로 확정한 후 대상 지역별로
허용해야 한다. 이는 법률 자문 전까지 보수적으로 처리할 영역이다.

여행상품 판매에 대해서는 관광진흥법상 여행업 등록이 중요한 Gate다.
관광진흥법 제4조는 여행업 등을 경영하려는 자의 등록을 규정하며,
여행업자는 시행규칙 제18조에 따른 보증보험·공제 또는 영업보증금 유지
의무를 검토해야 한다. 기획여행에는 추가적인 보증 요건도 규정되어 있다.
[5]

전자상거래에서는 JETPOOL이 직접 판매자인 거래와 Host/Guide/Supplier의
거래를 중개하는 경우를 계약·UI·원장에서 구분해야 한다. 현행 전자상거래
소비자보호법은 통신판매중개 개념을 두고 있으므로 상품 상세, 주문서,
영수증, 취소·환불 화면에 판매자/중개자 역할을 명확히 표시하도록 데이터
모델을 설계해야 한다. [27]

회계·세무는 merchant_of_record, supplier_type, commission, gross,
refund, tax_adjustment, net_payout을 분리 저장한다.
부가세·원천징수·세금계산서·현금영수증의 정확한 적용은 Host가 개인인지
사업자인지, Guide가 사업자인지, JETPOOL이 직접 판매자인지 중개자인지에
따라 달라질 수 있으므로 세무사 확정 전에 하나의 일률적 세율을 코드에
하드코딩해서는 안 된다.

보험은 법정 영역과 운영상 권고를 구분한다. 여행업자의
보증보험·공제/영업보증금은 관련 법령에 따른 검토 대상이고, 그와 별개로
플랫폼 배상책임, 사이버, 숙소 재산손해·Host liability, 여행자 상해보험
등은 사업 리스크 관리 측면에서 별도로 검토한다. [28]

                                                                generated/, CHANGELOG.md

  jetpool-infra           Terraform/Helm/CI                     terraform/, helm/,
                                                                environments/, runbooks/,
                                                                scripts/
  -----------------------------------------------------------------------------------------

각 저장소의 AGENTS.md에는 최소한 도메인 불변식, 허용 상태전이, API
source-of-truth, 금지사항, 테스트 명령, DB migration 규칙, 보안조건을
기록한다. Smoobu Booking Engine 역시 AGENTS.md를 AI coding agent용
“architecture, data model, API contract”의 핵심 문서로 사용하고 있어 이
패턴을 그대로 발전시킬 가치가 있다. [10]

원클릭 AI 기반 코드 생성 플로우

생성된 코드와 구현을 그 계약에 맞추는 것이다.

GitHub Actions CI/CD 템플릿

다음은 서비스 공통 reusable workflow의 초기 예다.

    name: jetpool-ci

    on:
      pull_request:
      push:
        branches: [main]
      workflow_dispatch:
        inputs:
          deploy_environment:
            description: Deployment environment
            required: false
            default: staging
            type: choice
            options:
              - staging
              - production

    permissions:
      contents: read
      id-token: write

    env:
      NODE_VERSION: "22"

    jobs:
      quality:
        runs-on: ubuntu-latest

        services:
          postgres:
            image: postgres:17
            env:
              POSTGRES_USER: jetpool
              POSTGRES_PASSWORD: jetpool_test
              POSTGRES_DB: jetpool_test
            ports:
              - 5432:5432
            options: >-
              --health-cmd "pg_isready -U jetpool"
              --health-interval 10s
              --health-timeout 5s
              --health-retries 5

          redis:
            image: redis:7
            ports:
              - 6379:6379

        steps:
          - name: Checkout
            uses: actions/checkout@v4

          - name: Setup pnpm
            uses: pnpm/action-setup@v4

          - name: Setup Node
            uses: actions/setup-node@v4
            with:
              node-version: ${{ env.NODE_VERSION }}
              cache: pnpm

          - name: Install
            run: pnpm install --frozen-lockfile

          - name: Lint
            run: pnpm lint

          - name: Type check
            run: pnpm typecheck

          - name: Unit tests
            run: pnpm test:unit

          - name: Database migrations
            run: pnpm db:migrate
            env:
              DATABASE_URL: postgres://jetpool:jetpool_test@localhost:5432/jetpool_test

          - name: Integration tests
            run: pnpm test:integration

          - name: Build
            run: pnpm build

      container:
        if: github.ref == 'refs/heads/main'
        needs: quality
        runs-on: ubuntu-latest

        steps:
          - uses: actions/checkout@v4

          - name: Build image
            run: |
              docker build \
                --tag jetpool-service:${{ github.sha }} \
                .

          # 실제 환경에서는 registry login 후 immutable SHA tag push
          # 장기 cloud access key 대신 GitHub OIDC 사용 권장

      deploy-staging:
        if: github.ref == 'refs/heads/main'
        needs: container
        runs-on: ubuntu-latest
        environment: staging

        steps:
          - uses: actions/checkout@v4

          - name: Terraform plan/apply
            working-directory: infra
            run: |
              terraform init
              terraform validate
              terraform plan -out=tfplan
              terraform apply -auto-approve tfplan

          - name: Smoke test
            run: ./scripts/smoke-test.sh staging

      deploy-production:
        if: >
          github.event_name == 'workflow_dispatch' &&
          inputs.deploy_environment == 'production'
        needs: quality
        runs-on: ubuntu-latest
        environment: production

        steps:
          - uses: actions/checkout@v4

          - name: Deploy immutable release
            run: ./scripts/deploy.sh production "${GITHUB_SHA}"

          - name: Production smoke test
            run: ./scripts/smoke-test.sh production

Production 환경에는 GitHub Environment protection을 적용해 결제·DB
migration이 포함된 Release가 자동으로 무인 배포되지 않도록 한다.
workflow_dispatch → production approval → immutable SHA image → canary → smoke → full rollout을
상용 기준으로 삼는다.

최종 개발 기준선

제트풀의 핵심은 다음 세 시스템을 잘못 합치지 않는 것이다.

                 ┌───────────────────────┐
                 │      JETPOOL ID       │
                 │ User / Trust / Review │
                 └───────────┬───────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
            ▼                ▼                ▼
      Paid Stay         Home Exchange     Guide Friend
     Reservation        Mutual Agreement  Social/Service
         FSM                 FSM               FSM
            │                │                │
            └────────────┬───┴───────────────┘
                         ▼
                 Shared Calendar
                         │
                         ▼
            Payment / Ledger / Settlement
                         │
                   ┌─────┴─────┐
                   ▼           ▼
               Toss PG       Payout

즉, 숙박 예약은 “재고+결제”, Home Exchange는 “상호제안+상호합의+두 숙소
일정잠금”, Guide Friend는 “사람+시간+유/무료 유형+안전검증”의 문제다. 세
도메인이 동일한 User, Trust, Chat, Review, Notification, Calendar,
Payment 인프라를 공유하되 각자의 상태머신은 독립적으로 유지해야 한다.

그리고 현재 wontc.co.kr이 이미 제시하고 있는 집 맞교환, 현지 생활,
JETPOOL 전세기 공유, 투어·티켓 등의 브랜드 자산은 폐기할 대상이 아니라
새로운 거래 플랫폼의 상위 Information Architecture로 이전할 자산이다.
기존 사이트가 설명 중심이라면 신규 JETPOOL은 그 설명을 실제
Search → Match → Agreement/Booking → Payment → Experience → Review → Settlement
거래로 완성하는 것이 이번 리모델링의 본질이다. [1]

1차 상용화 아키텍처 결론은
Next.js + PostgreSQL/Supabase + Jetpool Booking/Exchange/Guide Domain + TossPayments + Meilisearch + MapLibre + Payload + Novu + Chatwoot
조합이며, wrujel Airbnb Clone은 UI/UX 자산, Smoobu Booking Engine은 예약
상태·idempotency·Terraform 자산, QloApps는 PMS 업무규칙, Medusa는 커머스
primitives를 가져오는 구조가 가장 합리적이다. 각 오픈소스의 전체 코드를
하나로 병합하기보다 Jetpool의 OpenAPI·DB Schema·Domain Event를 먼저
고정하고 필요한 패턴만 이식하는 방식이 장기적인 상용화와 유지보수에
유리하다. wrujel은 숙소·필터·지도·예약 UI를 구현하고 있고, Smoobu 엔진은
durable booking state machine과 webhook/idempotency를 구체화하며,
Medusa는 commerce building blocks를 제공하고, QloApps는 PMS/Booking
Engine을 제공한다. [29]
