1. Executive Summary

1차 백서는 JETPOOL을 단일 Airbnb Clone 확장이 아니라 Paid Stay, Home
Exchange, Guide Friend, Travel Commerce를 하나의 ID·신뢰·결제·채팅·운영
체계로 묶는 다중 Marketplace로 정의하고, 예약/교환/가이드의 상태와 법적
책임을 분리해야 한다는 구조를 제시했다. 2차 백서는 이 방향을 유지하면서
실제 개발 단계에서 AI와 사람 개발팀이 해석을 달리하지 않도록 기능, UI,
API, 데이터, 이벤트, 상태머신, 테스트, Release Gate를 하나의 추적 가능한
구현 명세로 통합한다.

  -----------------------------------------------------------------------
  2차 핵심 결론
  “원클릭 개발”의 실질적 의미는 모든 기능을 한 번에 무검증으로
  Production에 넣는 것이 아니라, 명세를 Source of Truth로 삼아
  코드·테스트·IaC를 반복 생성하고 Staging까지 자동 검증한 후 Production만
  사람이 승인하는 구조다. 이 방식이 기능 누락과 AI 임의 해석을
  최소화한다.
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

-   Paid Stay는 재고·Hold·결제·취소·환불이 결합된 Reservation FSM으로
    구현한다.

-   Home Exchange는 상호 제안·반대제안·상호수락·검증·동일 약정 버전
    동의·두 숙소 Calendar lock을 갖는 별도 Aggregate로 구현한다.

-   Guide Friend는 FRIEND / VOLUNTEER / PAID / PROFESSIONAL 유형을
    분리하고 유료 유형만 결제·사업자/자격 Gate를 연계한다.

-   기존 WONT의 여행 콘텐츠·멤버십·전세기 공유 브랜드 자산은 버리지 않고
    IA로 이전하되, 전세기 직접 거래 기능은 사업·법적 범위 승인 전
    Feature Flag OFF로 둔다.

-   PostgreSQL은 거래 사실의 권위 데이터이며,
    Meilisearch/Redis/Realtime/AI 추천은 재생성 가능한 보조 계층이다.

-   Payment/Refund/Ledger/Settlement는 예약 상태와 분리된 금융
    도메인으로 만들고, PG 결과를 서버에서 재검증한 후 예약을 확정한다.

JETPOOL은 고객·공급자·운영자를 하나의 플랫폼으로 연결하되 외부

그림 2. 논리 컨테이너/서비스 구조

3.1 경계 원칙

-   비즈니스 상태는 각 도메인 서비스와 PostgreSQL에만 기록한다.

-   BFF는 UI 편의용 조합을 제공하지만 Booking/Exchange/Guide의 핵심
    상태를 중복 소유하지 않는다.

-   서비스 간 동기 호출은 사용자 요청의 즉시 검증에 한정하고, 검색
    동기화·알림·분석·비핵심 후처리는 Outbox 이벤트로 분리한다.

-   초기에는 동일 Managed PostgreSQL cluster 내 schema 분리를 허용하지만
    테이블 소유권을 명확히 하여 향후 분리 가능성을 보장한다.

-   Kubernetes는 성장 단계에서 도입 가능하도록
    컨테이너/healthcheck/12-factor 규칙을 지키되 MVP부터 운영 복잡도를
    강제하지 않는다.

그림 3. 예약/결제 핵심 시퀀스

DRAFT → QUOTED → HELD → PAYMENT_PENDING → CONFIRMED → CHECKED_IN →
COMPLETED
↘ PAYMENT_FAILED / EXPIRED
CONFIRMED → CANCELLED → REFUND_PENDING → PARTIALLY_REFUNDED | REFUNDED
COMPLETED → DISPUTED

-   동일 property와 겹치는 기간의 ACTIVE inventory block은 capacity를
    초과하지 않는다.

-   Hold는 TTL이 있고 만료 시 block을 해제한다. 결제 처리 중 TTL 정책은
    별도 ADR로 고정한다.

-   CONFIRMED 전이는 서버의 PG 승인/조회 결과, 내부 order/quote 금액,
    currency, subject ID가 일치할 때만 허용한다.

-   환불은 Payment 도메인에서 처리하고 Reservation은 환불 결과 이벤트를
    받아 표시 상태를 갱신한다.

REQUESTED → OFFERED/COUNTERED → ACCEPTED → [PAID: PAYMENT_PENDING →
CONFIRMED] | [FREE: CONFIRMED] → IN_PROGRESS → COMPLETED → REVIEWED
각 단계에서 CANCELLED / DISPUTED 분기 가능

FRIEND/VOLUNTEER는 원칙적으로 무료 흐름, PAID/PROFESSIONAL은
가격·결제·자격/사업 검증이 필요한 흐름으로 분리한다.

7.4 Payment / Refund / Settlement

Payment: CREATED → CONFIRMING → APPROVED | FAILED | CANCELLED
Refund: REQUESTED → PROVIDER_PENDING → PARTIAL/REFUNDED | FAILED
Settlement: DRAFT → READY → APPROVAL_PENDING → APPROVED → PAYOUT_PENDING
→ PAID → RECONCILED | HELD

8.1 데이터 분류와 보존

-   Class A: 금융·감사·계약 증거 — 법적/회계 보존 정책에 따라 삭제 대신
    제한·분리보관 가능하도록 설계.

-   Class B: 계정 PII — 목적/동의/보존기간에 따라 암호화·접근로그·삭제
    workflow.

-   Class C: 공개 Marketplace 콘텐츠 — publish 상태와 moderation 기록
    유지.

-   Class D: 캐시/검색/추천 feature — 원천 데이터에서 재구축 가능해야
    하며 권위 데이터로 사용하지 않음.

9. API / Event Contract 규약

-   OpenAPI 3.1을 동기 API Source of Truth로 사용하고 generated
    client/type을 직접 수정하지 않는다.

-   AsyncAPI 3.0을 도메인 이벤트 카탈로그로 사용한다. 이벤트에는
    eventId, eventType, version, aggregateId, correlationId,
    causationId, occurredAt을 포함한다.

-   Mutation API는 중요한 중복 위험이 있는 경우 `Idempotency-Key`를
    요구한다.

-   오류는 RFC 7807 형태의 Problem object를 기본으로 사용하고
    correlationId를 노출한다.

-   외부 provider webhook은 raw body 검증 요구를 고려하고 처리 결과와
    원본 hash를 보존한다.

  auth scope, examples, error codes를 모듈별 ADR과 함께 완성해야 한다.

12. 결제·환불·원장·정산

PG 결제와 공급자 정산을 분리한다. Payment는 provider fact를 기록하고,
Ledger는 플랫폼 경제적 사실을 기록하며, Settlement는 Ledger에서 특정
payee/기간의 지급 가능 잔액을 집계한다. 예약·가이드·여행 주문은 Payment
ID를 참조하지만 금융 원장을 직접 수정하지 않는다.

-   금액은 minor unit integer로 저장하고 currency를 항상 함께 저장한다.

-   결제 confirm은 order/quote 내부 금액과 provider 금액 일치 검증 후
    승인한다.

-   부분 환불 누계는 승인 결제액을 초과할 수 없다.

-   정산은 gross, platform fee, refund, tax adjustment, reserve/hold,
    net payout을 분리 표시한다.

-   정산계좌 변경, 수동 refund, settlement approve, payout execute는
    AAL2 + 감사로그 + 최소권한 정책을 적용한다.

부록 C. 출처 및 변경 구분

본 v2의 베이스는 사용자가 첨부한 「제트풀 상용 플랫폼
마이그레이션·리모델링 기술 백서 초안」이다. 해당 문서가 정의한 목표,
도메인 분리, 핵심 스택, 상태머신, 마이그레이션, 보안, 한국 규제 Gate,
테스트, 8-repository 방향과 원클릭 AI 원칙을 유지했다. v2에서 추가된
내용은 기능 추적성, UI route inventory, machine-readable build spec,
API/Event/DB seed, 추가 상태머신, Release Gate, AI agent 역할 분할 및
운영 KPI다. 외부 법률·서비스 버전은 본 작업에서 재검증하지 않았으므로
실제 출시 직전 최신 공식 자료로 재확인해야 한다.
